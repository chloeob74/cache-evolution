# Evolving Cache Replacement Policies with OpenEvolve

*A mini-OpenEvolve study: can an LLM-driven evolutionary loop improve on human-written cache policies, and what does it teach us about AI-driven optimization of systems code?*

---

## 1. Introduction

Caches sit on the critical path of nearly every data system, and the policy that decides what to evict when the cache is full directly determines the hit rate, and therefore latency and downstream load. Decades of research have produced a zoo of hand-designed heuristics (LRU, LFU, FIFO, SLRU, 2Q, GDSF, ARC, …), each trading simplicity against workload sensitivity. Designing a good policy is a classic example of *algorithmic structure search*: the space of correct policies is large, the objective (hit rate) is easy to measure, and the "right" answer is workload-dependent.

This project asks a focused question: can an LLM-driven evolutionary coding loop, given only a naive baseline and a scoring function, rediscover or improve on human-written cache policies — and where does that process succeed or fail?
I build a mini version of OpenEvolve using the open-source [OpenEvolve](https://github.com/codelion/openevolve) framework, seed it with a plain LRU cache, and let Claude Sonnet 4.6 mutate the eviction logic over 50 iterations against a real storage trace. I then compare the evolved policy against two human baselines (LRU, LFU) and against a clairvoyant optimal (Belady/MIN) that bounds how good *any* policy could be.

The deliverable is threefold: a working pipeline, a quantitative comparison, and, most importantly, an analysis of what kinds of problem structure make this kind of AI-driven of ptimization easy or hard, including the failure modes (constraint gaming, reward miscalibration, overfitting) that emerged along the way.

## 2. System Design

The system is a constrained optimization loop with five decoupled parts:

| Component | Role | File |
|---|---|---|
| **Seed program** | The baseline algorithm the search starts from (LRU), with the mutable region fenced by `EVOLVE-BLOCK` markers | `initial_program.py` |
| **Evaluator** | Defines correctness + the scalar reward: replays a trace and returns `hit_rate × time_factor` | `evaluate.py` |
| **Prompt** | Domain knowledge given to the LLM each iteration (constraints, worked examples, strategy menu) | `prompt.txt` |
| **Controller** | OpenEvolve itself: samples a parent, asks the LLM for a mutation, evaluates it, stores it | OpenEvolve pkg + `config.yaml` |
| **Reference policies** | Human baselines and the clairvoyant ceiling for comparison | `cache_simulator.py`, `compute_optimal.py` |

**Evolutionary engine.** OpenEvolve's style is that of an evolutionary coding agent OpenEvolve implements an AlphaEvolve-style loop over a MAP-Elites database with island-based evolution. Each iteration runs in a worker process: it samples a parent program from an island (which helps with diversity of mutations), builds a prompt (baseline + evolution history + top performers), asks the LLM for a code mutation, runs the evaluator, and proposes promising new mutations with an evolutionary search (SOURCE: https://arxiv.org/html/2606.01975v1). We configured 3 islands, a population cap of 100, and 50 iterations.

**The LLM as mutation operator.** Mutations are generated by **Claude Sonnet 4.6**, called directly through Anthropic's OpenAI-compatible endpoint (`https://api.anthropic.com/v1/`) at temperature 0.7. Only the code between the `EVOLVE-BLOCK-START/END` markers (the `__init__` and `access` methods) is mutable. The `hit_rate()` accounting is frozen so candidates cannot cheat the metric directly.

**Rewarding Systems** The score is deliberately multi-objective:
`score = hit_rate × time_factor`. `time_factor` rewards fast evaluation (1.05× under 2 s), and is neutral up to 25s. Any `score` with a 'time_factor' beyond 25s is applied a graduated penalty, and is **halved** if a candidate falls below the LRU baseline hit rate. The intent is to push toward high hit rate *and* practical, low-overhead code, while strongly discouraging regressions.

## 3. Implementation Details

**Workload.** We use `msr_hm_0`, a real Microsoft Research block-storage trace in the `oracleGeneral` format (24-byte records: `<IQIq` = timestamp, object id, object size, next-access). The evaluator decompresses the trace and replays the first **50,000 requests**. Caching is **byte-based** (objects have variable size), which makes the problem strictly harder than the textbook fixed-slot version as eviction must free enough bytes, and "optimal" becomes NP-hard.

**Cache size became the most important design choice.** Our first runs used a **64 MB** cache and showed almost no improvement. The reason, established with `compute_optimal.py`, is that the workload was *LRU-friendly* at that size: the Belady/MIN clairvoyant ceiling was only **1.5 pp** above LRU, so there was essentially nothing for the optimizer to find. Sweeping the cache size revealed that shrinking to **16 MB** opens a **7.31 pp** headroom band between LRU (0.479) and MIN (0.552), as well as fliping the baseline ordering (LFU overtakes LRU). All reported results use the 16 MB configuration. *This became the single most consequential implementation decision in the project*, and is itself a finding (Section 5).

**Seed program.** The search starts from a straightforward byte-based LRU built on `OrderedDict` (`move_to_end` on hit, `popitem(last=False)` to evict the least-recently-used item until the new object fits).

**Evaluator and correctness.** `evaluate.py` loads the candidate's `EvolvedCache` class, instantiates it at 16 MB, replays the 50k records, and returns the scored result plus debugging *artifacts* (final size, item count, hit/miss totals, `time_factor`). Correctness is enforced structurally: the frozen `hit_rate()` method and the harness's own hit/miss bookkeeping mean a candidate is only credited for genuine hits. A wall-clock timeout aborts pathological candidates. The below-baseline penalty is calibrated to `BASELINE_HIT_RATE = 0.4790`, just under the measured LRU rate so LRU-equivalent policies are not self-penalized.

**Prompt engineering.** `prompt.txt` supplies the LLM with the domain framing, an explicit **O(1)-per-operation eviction constraint**, a worked SLRU example using two `OrderedDict`s, a menu of strategies to explore (SLRU ratios, frequency buckets, 2Q, size-aware eviction), and lessons learned (timeouts come from O(n) eviction scans).

**Baselines and ceiling.** `cache_simulator.py` provides clean human implementations of LRU, LFU (O(1) frequency buckets) and FIFO. `compute_optimal.py` computes the **Belady/MIN** reference with a lazy-deletion max-heap on next-use distance; because true optimal for variable-size caches is NP-hard, it uses the standard furthest-next-use heuristic (evict the item needed farthest in the future; don't evict a sooner-needed item to admit a later-needed one). These baselines are computed on the *identical* trace slice and cache size, so the comparison is apples-to-apples.

**Visualization.** `visualize.py` reads the program database and logs, computes the baselines live, and emits a single interactive HTML report (`evolution_report.html`) with the headline comparison, score/hit-rate frontiers, the scoring-threshold view, the evolution tree, per-island trajectories, a glossary, and context KPIs.

**Cost / billing note.** OpenEvolve makes one LLM call per iteration with no prompt caching. The Anthropic key is kept out of the global environment (injected per-command from a mode-600 file) so the developer-API spend for the evolution runs stays separate from the Claude Code subscription.

## 4. Evaluation Results and Key Findings

**Headline result.** The most recent 16 MB run (stopped at iteration 46 of 50; **0 timeouts, 0 errors**) produced a best policy at **iteration 38** that comfortably beats both human baselines and captures most of the available headroom:

| Policy | Hit rate | vs LRU | Notes |
|---|---:|---:|---|
| LRU (seed) | 0.4793 | — | byte-based LRU |
| LFU | 0.5036 | +2.43 pp | human baseline |
| **Evolved (GDSF + admission)** | **0.5311** | **+5.18 pp** | LLM-discovered |
| Belady/MIN | 0.5523 | +7.31 pp | clairvoyant ceiling (not realizable) |

The evolved policy sits at **71% of the LRU→MIN headroom** (i.e. it closes roughly three-quarters of the gap between the naive baseline and the theoretical optimum). Re-scored under the corrected baseline, the headline numbers are hit rate **0.5311**, combined score **0.5576**, evaluation time **0.064 s**.

**What the evolution discovered.** The winning program is a **Greedy-Dual-Size-Frequency (GDSF)** policy with three ingredients:

1. a priority `clock + freq/size` (favor small, frequently-used objects; the
   "clock" ages priorities so stale high-priority items eventually fall);
2. a **lazy-deletion min-heap** for eviction (rather than the forbidden O(n) scan);
3. a **one-hit-wonder admission filter** that refuses brand-new objects when the
   cache is full, plus frequency counts that **persist across evictions** (ghost
   history), so an object's track record survives being evicted once.

**Trajectory.** Progress was front-loaded: seed (penalized artifact) -> **0.5038 at iteration 1** (the admission filter alone already beats LFU) -> 0.5288 (it 3) -> 0.5548 (it 17) -> 0.5576 (it 38). The first mutation captured the bulk of the gain; later iterations were refinement with diminishing returns.

### Key findings

**(a) Benchmark headroom, not the optimizer, decides whether AI search "works."** On the 64 MB workload the loop ran identically but found almost nothing, because MIN was only 1.5 pp above LRU. The same pipeline on a 16 MB cache produced a 5 pp win. The lesson is uncomfortable for "AI improved our algorithm by
X%" claims: the result was largely determined before the LLM ran, by a human choice (cache size relative to working set) that set how much signal existed.

**(b) The AI rediscovered known human structure, it did not invent new structure.** GDSF and admission filtering are textbook techniques. The model converged on a known-good design quickly and reliably — convergent rediscovery, not novelty. That is genuinely useful (it's a fast, competent autotuner), but it is not algorithmic discovery in the AlphaEvolve "new lower bound" sense.

**(c) The reward function is the real program — and proxies get gamed.** The scoring used wall-clock time under 2 s as a *proxy* for the stated O(1) complexity constraint. Because they are not the same thing, candidates exploited the gap: the evolved policy uses an O(log n) heap (and an earlier 64 MB run used a
bounded O(512) scan) — both technically violate "O(1) per operation" yet sail under the 2 s threshold at 50k records and pocket the speed bonus. The optimizer optimized exactly what we measured, not what we meant.

**(d) Reward calibration is brittle.** The below-baseline penalty has a hard boundary at the LRU hit rate. Because byte-based LRU lands at 0.47926 and an early threshold was set at 0.4793, the seed penalized *itself* (score halved, 0.2516 instead of ~0.50) — a 2× swing from a 0.0001 miscalibration. Small errors in reward design produced large, misleading score artifacts.

**(e) Single-trace evaluation invites overfitting.** All scoring used one 50k slice of one trace. The evolved policy is tuned to that workload; we did not validate on held-out traces, so some of the 5 pp could be benchmark-specific.

**(f) What made the task *easy* for the AI:** the mutable surface was small, local, and well-encapsulated; the objective was a single fast scalar with tight feedback (~one evaluation per iteration, sub-second); and the domain (cache policy) is dense in the model's training data, giving it strong priors. **What made it *hard*:** constraints that live *outside* the objective (asymptoticcomplexity), objectives with little  headroom, and multi-objective trade-offs that a proxy metric can short-circuit.

## 5. Conclusion: Implications for AI / Data Systems

This study shows that an LLM-driven evolutionary loop can, with modest compute, match and exceed expert-written heuristics for a self-contained systems component — here closing 71% of the gap between naive LRU and the clairvoyant optimum on a real storage trace. For data systems, that is an encouraging signal: many performance-critical components (cache eviction, prefetching, scheduling heuristics, query-planner cost tweaks, compaction policies) are exactly this shape — a small, well-isolated decision function with a measurable objective. Workload-specialized policies, regenerated automatically when the workload shifts, are a plausible near-term application.

But the project's sharper lesson is about **where human effort moves**, not whether the AI "works." Across every finding, the leverage was in the *framing*: choosing a benchmark with real headroom (the 64 MB → 16 MB decision mattered more than any model capability), and designing an evaluation harness that the optimizer cannot game. An LLM in an evolutionary loop is a relentless literalist: it will exploit a wall-clock proxy instead of honoring an asymptotic constraint, it will surface miscalibrated reward boundaries as "wins," and it will overfit a single trace if that is all you score. **The evaluator, not the seed program, is the real artifact you are building** — its correctness checks, its invariants, and its choice of objective are what determine whether the evolved code is trustworthy.

For AI-driven optimization of systems code to be deployable, the harness therefore needs what this prototype only partially had: invariants enforced *directly* (e.g. actually measure asymptotic behavior or cap data-structureoperations, rather than proxying with wall-clock), evaluation across *multiple held-out workloads*, and reward functions robust to boundary effects. With those guardrails, LLM-driven evolution is a credible tool for autotuning the long tail of heuristics inside data systems. Without them, it is an extremely efficient machine for producing impressive-looking numbers that do not generalize. The
algorithmic structure that is *easy* for AI to optimize — local, measurable, prior-rich — is common in systems work; the discipline required to optimize it *honestly* is the harder, and more human, half of the problem.

### Appendix: Reproduction

```bash
# Run the evolution (16 MB, 50 iterations, Sonnet 4.6)
./run_evolution.sh 50

# Compute the human + clairvoyant baselines
python compute_optimal.py

# Regenerate the interactive report
python visualize.py            # -> evolution_report.html
```

Key configuration: `config.yaml` (3 islands, population 100, 50 iterations), `evaluate.py` (16 MB cache, 50k records of `msr_hm_0`, `score = hit_rate × time_factor`). Best evolved program: `openevolve_output/best/best_program.py`.
